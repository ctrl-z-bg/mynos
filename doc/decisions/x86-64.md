# Decision: MyNOS on x86-64

- **Issues:** mynos-btq.3, in the version 2 line (mynos-btq)
- **Date:** 2026-11-25
- **Status:** accepted by the owner (2026-11-25). On branch `x86-64`:
  MyNOS boots on x86-64 to the shell (2026-11-25): `init`, every
  service, `sh` and the OCaml toplevel at 64 bits (`Sys.word_size` 64).
  The test suite passes at 64 bits (181 checks, 2026-11-25), and the
  scripts run either architecture (`ARCH=x86_64`).

## What changes, and what does not

Above the kernel almost nothing: OCaml's bytecode does not depend on
the processor, the protocols are defined byte by byte, and the C
services are rebuilt by a 64-bit toolchain. The kernel, `libmynos`'s
native calls and the start code change. i386 keeps building and passing
the suite in the same tree (`ARCH=i386`, the default, and
`ARCH=x86_64`), as `doc/decisions/arch.md` planned.

## Choices

**1. The toolchain.** A second container, `dev-x86_64`: the same Debian,
gcc, musl and OCaml 5.5.2 as `dev`, for amd64 (63-bit OCaml integers:
the ids below 2^30 stop being a limit). `tools/in-container.sh` and
`build-image.sh` pick the platform from the image's name.

**2. The boot.** GRUB and QEMU's `-kernel` start a multiboot kernel in
32-bit protected mode, and QEMU loads only 32-bit ELF files. The kernel
is linked as a 64-bit ELF and copied into a 32-bit container
(`objcopy -O elf32-i386`, a common trick); `arch/x86_64/start.asm`
begins in 32 bits, builds the first page tables, turns on PAE, long
mode and paging, and jumps to 64-bit C.

**3. The address space.** All of physical memory mapped once in the
higher half, the programs in the lower half; the kernel's image where
the i386 has it, so that the two layouts differ as little as they can:

```
  0xFFFF800000000000  all of physical memory, mapped once (the "direct
                      map"): the kernel reaches any page, and any page
                      table, through it
  ...                 (non-canonical hole)
  0x00007FFFFFFFF000  the user stack's top
  0x0000000040000000  the program, as on i386
  0x0000000000200000  the kernel's image (the low gigabyte, the kernel's
                      only, in every address space, as on i386; gcc's
                      small code model: addresses below 2 GB)
```

The i386's tricks go: no page directory mapped on itself (the
recursive last entry), no one-page windows to reach another process's
frame or a page being copied: the direct map reaches them all. The
4 MB limit of a program, the 3.5 GB limit of memory, go with them.

**4. The interface to page tables** (`arch.h`), so that `mem/`, `fork`
and the external pager stop walking an i386 page directory:
`arch_pte` (the entry of a linear address in an address space, made if
asked), `arch_map`, `arch_unmap`, `arch_new_space` (the kernel's half
shared), `arch_free_space`, `arch_copy_space` (fork: every present
entry copy-on-write), `arch_switch_space`, and the entry's bits as
generic flags (present, writable, user, and MyNOS's own: logically
present, copy-on-write, shared, pager). i386 implements them with its
two levels and its recursive entry, as today; x86-64 with four levels
through the direct map. This is the largest part of the work.

**5. The thread and its registers.** `tss_t` stops being both the thread
and the processor's task state segment: a `thread_t` (generic: ids,
semaphores, TLS, timers, queues) holds an `arch_context` (i386: the
registers it has today; x86-64: rbx, rbp, r12-r15, rsp, rip, the FPU
area, and FS's base for TLS). One TSS per processor, for the kernel's
stack on entry.

**6. System calls.** Linux's x86-64 ABI (`syscall`, its own numbers,
arguments in rdi, rsi, rdx, r10, r8, r9), which musl uses; MyNOS's
native calls stay `int 0x90`, with 64-bit arguments in the same
registers. `libmynos`'s 66 casts of pointers to `int` become `long`.
The handlers stay generic: only the entry and the table of numbers are
the architecture's.

**7. Types.** Addresses in generic kernel code become `uintptr_t`
(`vaddr_t`, `paddr_t`); `uint32_t` stays for what is 32 bits by nature
(protocol fields, ELF32 headers on i386).

## The order of work

1. The container; a 64-bit kernel that boots, prints, and stops
   (`start.asm`, the direct map, serial and VGA).
2. The types (`vaddr_t`, `paddr_t`) through generic code, i386 still
   green.
3. The page-table interface (choice 4), i386 first, still green; then
   x86-64's.
4. Interrupts, the timer, the thread split (choice 5), the scheduler.
5. ELF64 programs, the system calls (choice 6), `libmynos`, the first
   64-bit program; then `ocamlrun`, the services, the suite.

## What it took, and what it found

- **The build.** `tools/build-x86_64.sh` copies the tracked sources to
  `build/x86_64/tree` and runs `build-all.sh`'s commands there in the
  `dev-x86_64` container, the kernel's by `tools/build-kernel-x86_64.sh`:
  the two architectures' objects never meet.
- **The kernel** (`arch/x86_64`): `start.asm` (multiboot, long mode),
  `entry.asm` (exceptions, `int 0x90`, `syscall`, `trap_return`,
  `switch_stacks`, `copy_user`), GDT and the one TSS, a 64-bit IDT,
  the context switch (FS's base, FXSAVE), `mm.c` (the kernel's gigabyte
  with its page tables made at boot and shared; four levels through the
  direct map), `space.c` (ELF64, fork, freeing), `externalmem.c`,
  `calls.c` (the native calls and Linux's x86-64 calls by number, with
  adapters for mmap, stat, the times, `arch_prctl`), `thread.c` (the
  idle thread, a thread's first frame, `clone`).
- **Kernel stacks are the kernel's.** On the i386 a thread's kernel
  stack is in its process's space; switching address spaces there works
  because the task switch is done before the stack is left. On x86-64
  the switch loads the new space while still on the outgoing thread's
  stack: every kernel stack must be mapped in every space, so they are
  in the kernel's gigabyte (`ARCH_KSTACK_FLAGS`), freed with the
  process.
- **Generic code that was 32-bit without saying so**: the multiboot
  structures (`unsigned long`), `size_t`, addresses computed in 32 bits
  in `mem.c`, the pager's types, the RAM disk's directory (a `char *`
  for an offset: now `uint32_t`, the same bytes on the i386),
  `libmynos`'s pointers cast to `int` for the native calls, its raw
  Linux calls through `int 0x80` (`fileio.c`, `consoled`), a new
  thread's argument passed on the stack (`mynos_threadCreate`).
- **OCaml's `int` is wider than C's.** `Gfx.text`'s default limit is
  `max_int / 2`; the stub put it in an `int`, which at 64 bits made it
  −1, and no text was drawn. Stubs that take a value which may be near
  `max_int` clamp it.
- **An address in a 32-bit parameter.** The futex's timeout pointer was
  `uint32_t`: cut above 4 GB, refused, and every timed wait returned at
  once, so `netd` spun and every network request was four seconds late
  (JOURNAL). The other calls were checked for the same mistake.
